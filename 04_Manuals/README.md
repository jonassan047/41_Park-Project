# PARK

SES 企業どうしを1つのグループにまとめ、届いた案件に、グループ全体のエンジニアからいちばん合う人を出して、**エンジニアの成約率を上げる**ための Web アプリ。成約したときだけ成功報酬（初期費用・月額費用）をいただく仕組み。

構想・企画は [41_Park-Project](https://github.com/jonassan047/41_Park-Project)。2026-10-15 に、Node.js の試作（41_Park-Project の `81_PARKアプリ`）から PHP（Laravel 12）＋ MySQL（MariaDB）に移した。

## 動かし方（XAMPP）

- 場所：`D:\xampp\htdocs\park`、URL：http://localhost/park/
- DB：`jonassan_park`（MariaDB、utf8mb4）
- Apache：`httpd-vhosts.conf` に `Alias /park "D:/xampp/htdocs/park/public"` と、`public` の `<Directory>` に `RewriteOptions MergeBase`・`RewriteBase /park/`（ほかの Laravel アプリと同じ形）。

新しい PC で用意するとき：

```
composer install
copy .env.example .env
php artisan key:generate
php artisan migrate --seed
```

`--seed` で入るのは、技術マスタ（辞書）だけ。見本データは入らない。

架空の見本データを入れたいときは、手元でだけ次を動かす（パスワードはどれも `park1234`。公開版では何も入らない）。

```
php artisan db:seed --class=SampleSeeder
```

| 役割 | メールアドレス |
|---|---|
| 管理者 | admin@park.example |
| SES | ses1@park.example（みどり情報システム）、ses2@、ses3@ |
| エンジニア | eg1@park.example（山田）、eg2@（佐藤）、eg3@（鈴木） |

本番のデータで始めるときは `php artisan migrate:fresh --seed`（見本なし。**最初の1回だけ、データが無いときだけ使う。実在のデータが全部消える**）にして、最初の画面で管理者のアカウントを作る。管理者のダッシュボードは「PARK をはじめましょう」から始まり、SES・エンジニア・案件を実際に登録していく。

テスト用のダミーデータを入れるコマンド：`php artisan park:seed-dummy`（`SampleSeeder` とは別で、公開版でも動く）。オプションは `--ses`（SES の社数。既定 8）・`--staff`（担当者の人数。既定 15）・`--eg`（エンジニアの人数。既定 80）・`--direct`（うち管理者の直属の人数。既定はエンジニアの1割）・`--seed`（同じ値なら同じ名前・状態になる。無ければ乱数で決めて出力する）・`--yes`。`--yes` なしは予定の件数を出すだけで、何も変えない（名前・メールアドレスは出さない）。`--yes` で、1つの transaction で入れる（途中で失敗したら何も残らない）。メールは一切送らず、管理者のベル通知も増やさない。SES は申込中・参加中・停止、担当者とエンジニアは 参加中（本登録済み）・参加中（必須項目が足りない）・仮登録・仮登録（期限切れ）・停止中 が混ざる（SES の1社は仮登録で、SES だけ）。SES の会社名の末尾には「（ダミー）」が付く。メールアドレスは `ses-d01@park.example`・`eg-d001@park.example` の形で、番号は続きから振る（二重に実行しても重ならない）。ダミーのアカウントのパスワードは乱数で誰も知らないので、ログインはできない。消すときは `park:purge-samples`。ダミーの SES に本物の人（`@park.example` ではない人）を登録したり、ダミーのエンジニアで案件・応募を作ったりすると、purge は守りで止まる（`--move-kept-to-direct` か、管理者に確かめる）。ダミーがいる間は、一斉メールを使わない・案件の配信でダミーのエンジニア・SES を選ばない（応募まで進むと purge が止まる）。

見本データを消すコマンド：`php artisan park:purge-samples`。まず `--yes` なしで動かすと、表ごとの「消す件数」と「残す件数」と守りの判定が出る（何も変えない。名前・メールアドレスは出さない）。`--yes` を付けると、消す行を `storage/app/backups/purge-samples-日時.json` に書き出してから、1つの transaction で消す。見本の人（メールアドレスが `@park.example` の人）以外に使える管理者がいない、見本の SES に見本ではない人が入っている（`--move-kept-to-direct` を付けたときだけ管理者の直属へ移して続ける）、見本ではない案件に見本のエンジニアの応募・契約がある、のどれかのときは、何も消さずに止まる。消すものが0件なら何も変えない。

氏名とふりがなは、姓と名に分けて持つ（`name_sei`・`name_mei`・`kana_sei`・`kana_mei`）。`name`・`kana` は、姓＋名をつないだもので、画面の表示・メールの宛名・検索はこちらを読む。登録済みの人は、マイグレーションで空白（半角・全角）を区切りに分けて入れる。自分の登録情報は、アカウントの「登録情報を見る」（`/account/profile`）で見られる。

- **管理者**：ダッシュボード（やること・面談の予定・終わりが近い契約・今月の成功報酬）、管理者の一覧・仮登録（企業名・氏名・メールの4つ。別画面）・詳細・編集・送り直し・取り消し（上のメニューの「管理者」）、SES の仮登録・承認・送り直し・取り消し・停止、担当者・エンジニアの仮登録、エンジニアの検索、案件の登録（**案件メールの本文から項目を自動で抜き出す**。外部には送らない）、**マッチング**（点数・合う点・足りない点）と配信（メール）、選考のボード、面談の設定と**面談対策の Q&A の自動作成**（直せる）、成約・延長・終了・成約後のフォロー、**請求書**（初期費用・月額費用・消費税、印刷・PDF）、メールの送信箱と一斉配信、分析（応募→成約のファネル、SES ごとの成約率、見送りの理由、延長率）、設定（率は仮）、操作の記録、「管理者」の印（管理者がエンジニアとしても入るときの公平性のため）。
- **SES**：ダッシュボード、担当者・エンジニアの仮登録（ご本人に仮登録のご案内。担当者の登録は SES だけ）、グループ全体の案件と**自社エンジニアとの相性**、本人への案内・代わりに応募、選考の状況、契約、請求書、会社情報。
- **エンジニア**：仮登録のご案内から本登録（ふりがな・電話・住所・パスワード・**個人情報の取り扱いに同意**）、届いた案件（相性を見て、**条件を確かめて応募**／理由を選んで見送り）、プロフィール・スキル（**チェック式**。年数は4段階。**案件に当たる項目に「必須」「尚可」の印**）・経験票、**スキルシート**（案件に合わせて並べ替え、名前をイニシャルで伏せる版、印刷・PDF）、面談対策の Q&A と練習メモ、配属後のひとこと、管理者とのやり取り。
- 共通：通知（ベル）とメール、パスワードの変更・再設定。
- 同じ案件に、グループの中で同じ人が二重に応募することはできない。

## エンジニアの細かい登録・技術マスタ・データ領域（2026-10-16）

- エンジニアには、履歴書・業務経歴書の項目（生年月日・住所・電話・最寄りの路線と徒歩・最終学歴・職務概要・希望業務・語学・学歴/職歴・資格・アピール・本人希望）と、経歴の案件ごとの「機種・OS・ツール」「言語」「DB」を持たせる。
- **技術マスタ**（`skill_terms`）：案件とスキルを同じ「正式な名前」にそろえる辞書（分類・別名）。最初の辞書は `app/Support/SkillCatalog.php`、DB へは `php artisan park:skills-sync`（足りない言葉・別名・名前の変更・確認待ちの直し・経歴の索引の作り直し。行は消さない）。案件・スキルの「その他」にマスタに無い言葉が出たら自動で足し「確認待ち」にする（スキルは、その他に書いた名前だけ）（管理者の「技術マスタ」画面で確かめる）。
- **データ領域**：エンジニアごとに、最新の履歴書・業務経歴書（名前を伏せた版も）を Excel で書き出して保存・ダウンロードできる。アップロードもできる。置き場所は `storage/app/private/engineers/{id}/`（公開されない・Git に上げない）。見られるのは本人・所属 SES・管理者だけ。
- Excel の書き出しに PhpSpreadsheet を使う。PHP の `gd`・`zip` が要る（XAMPP は php.ini で有効にした）。

## 案件の案内メール（2026-10-16 tezzo）

SES が受けた案件メールから、エンジニアへの案内メールを出し、返事を受けて、案件をくれた先へ書類を返すまでの流れ（`app/Services/CaseMail.php`・`CaseMailController`）。

1. SES が案件を登録（案件メールの本文を貼って取り込む）
2. 候補を絞る：得意分野（スキル・経験票）から点数順に提案し、SES がチェックで足す・外す。自社のエンジニア（名前あり）と、グループのほかの人（名前を伏せる。プラスα）で画面を分ける
3. メールを作る：同じ内容／一人ずつ変える。差し込み（{呼び名} など）。呼び名は `engineers.nickname`（愛称）
4. 送る前に提案を出す（点数・足りないスキル・単価や開始日のずれ・過去の見送り）→ 送る。自社の人へは返信先（Reply-To）を SES の担当者にする。グループの人へは PARK から送り、その人の SES にも知らせる
5. 返事：自社の人は SES に直接返信が届き、SES が画面で記録する。本人が PARK の画面で応募・見送りをしたら自動で記録（`case_mails`）
6. 書類：「応募したい」の人の最新の履歴書・業務経歴書を、その場で Excel にしてダウンロード（グループの人は名前を伏せた業務経歴書だけ）

7. 書類を返したら「書類を返した（応募した）」で応募を作る → 面談依頼が来たら SES が記録（日時・場所・先方が確かめたいこと）→ 案件とスキルを突き合わせた面談スクリプトを作る（`Qa::generate`）→ 結果 → 成約。SES は自社の応募について、管理者と同じ手続きができる

8. 案件の画面の案内の入口は「エンジニアに案内する」だけ（2026-10-16 に「本人に案内」「応募を出す」「管理者の配信」をやめた。v0.7.0 から行き先は下の「エンジニア検索」で、古い `/cases/{id}/mail` の流れも URL を直接開けば残っている）。持ち込んでいない SES は「推薦する」（名前を伏せて知らせる）
9. 案内メールの最後に返事のリンク（`/r/{token}/{answer}`）。開くだけでは記録せず（メールソフトが先に開くことがあるため）、画面のボタンで記録して送った人に知らせる

### エンジニア検索（v0.7.0。2026-11-13）

案件の画面の［エンジニアに案内する］の行き先。メールから抜き出した必須・尚可でエンジニアを探し、一覧から案内メールを送る（`app/Services/CaseSearch.php`・`CaseSearchController`・`resources/views/cases/search*.blade.php`）。使えるのは今の案内と同じ人（`CaseMail::canSend`＝管理者と、案件を持ち込んだ会社の SES・担当者）。EG には画面ごと出ない（403）。

- **流れ**：検索画面（`GET /cases/{id}/search`。左に元のメール `raw_text`、右に必須・尚可。「外す」のチェックと、手入力で足す欄）→ 一覧（`/searches/{sid}`。チェック・全員へのメッセージ・［一覧に足す］）→ 詳細（`/searches/{sid}/members/{eid}`。条件ごとの ○×・個別メッセージ・メールの見本）→ ［エンジニアへメールを送信］（`POST /searches/{sid}/send`。ブラウザの確かめだけで、別の確認画面は無い）。
- **条件**：足した・外した条件は、その検索にだけ保存する（`case_searches.conditions`）。案件の必須・尚可・業務の列と技術マスタは変えない。技術は正式な名前にそろえ、マスタに無い言葉はそのまま（マスタには足さない）。業務の項目名と同じなら業務として扱う。開き直すと前の条件が入っている。案件を直したあとは、案件の列からの項目は案件の今の値で作り直し、足した項目と「外す」の印だけを引き継ぐ。
- **合格の決まり**：必須（技術＋業務）n 項目のうち当たった数 h が `h*4 >= n*3`（n=4 なら3つ）なら合格。必須が0項目なら全員合格。尚可は足切りしない。技術は `Matcher::hasSkill`（経歴だけで当たっても○）、業務は `SkillChecks::expMany`。
- **対象と並び**：対象は今の案内と同じ人（使える人・有効な SES・応募済みを除く・`unavailable` を除く。稼働中は入る）。並びは 自社 → 他社、それぞれ、当たった必須の技術の経験月数（経歴の月数と、スキルのチェックの年数の下限×12 の大きいほう）の合計 → h → 点数 → id。自社＝SES・担当者は自分の会社、管理者は直属（`kind=direct`）の会社。
- **名前の見え方**：他社の人は SES・担当者にはイニシャル（会社名）。管理者には氏名（会社名）。「一覧に足す」で探せるのも同じ範囲。条件に届かなかった人は人数だけ出す。
- **メール**：件名は `CaseMail::defaultSubject`、本文は `CaseSearch::defaultBody()`（今の案内の本文に、全員へのメッセージ・尚可・個別メッセージ・ご検討の一文を足したもの。雛形は直せない。空の欄は行ごと詰める）。必須に×がある人は、詳細画面に「［×の項目］に関しては○○様とご検討ください」を出す（SES への確認の注意書き。○○様＝そのエンジニア、他社の人はイニシャル。メールには入れない）。送る所は `CaseMail::send($u, $c, $items, 'search')` を通す（記録・返事のリンク・他社の SES への知らせは今の案内と同じ。`case_mails.mode='search'`）。同じ人に2回送らない。
- **表**：`case_searches`（案件×作った人で1行。条件・全員へのメッセージ）、`case_search_members`（一覧の人。チェック・手で足した印・個別メッセージ・一文を入れない印）。

## 連絡メール（v0.8.0。2026-11-13）

案件に結び付かない、人から人への自由な件名・本文のメール（`app/Services/DirectMail.php`・`DirectMailController`・`resources/views/mails/`）。案件の案内メール（`CaseMail`・エンジニア検索）や、管理者とエンジニアの「やり取り」（`/engineers/{id}/messages`。PARK の画面の中だけ）とは別で、どちらも残している。連絡メールは受け取った人にメールで届き、PARK の画面でも読める。

- **送れる範囲（1か所：`DirectMail`。画面の出し分けも送るときも同じ判定）**：管理者は全社のエンジニア（直属も）。SES・担当者は自社のエンジニアだけ。エンジニアは所属の会社の SES・担当者（`role=ses`）だけ（直属のエンジニアは管理者）。今回は無し：SES に所属するエンジニアから管理者へ、エンジニアどうし、SES どうし、管理者から SES・担当者へ。
- **宛先に出る人**：エンジニアは本登録済み・停止中でない・退会でない・アカウントがある人。SES・担当者・管理者は使えている人（SES は会社が参加中）。自分自身（兼任の人も）は出ない。選んだあとで停止・退会になった人は外して送り、「送れない n 名を外しました」と出す。範囲の外（他社のエンジニアの id・相手でない人の user id など）が混ざったら 403 で何も送らない。
- **入口**：管理者の `/admin/engineers`・SES の `/ses/engineers` の行のチェックと［選んだ人にメールを送る］（行の中に form があるので、チェックは表の外の `<form id="dm" method="get" action="/mails/new">` に `form="dm"` で結び付ける）。エンジニアの詳細（`/engineers/{id}`）の［メールを送る］（1人あて）。エンジニアのホームのカード［担当者にメールを送る］。ナビの「連絡メール」（一覧：受け取った・送った・管理者だけ「すべて」）。
- **ルート**：`GET /mails`・`GET /mails/new`（管理者・SES は `eg[]`＝エンジニアの id、エンジニアは `to[]`＝相手の users.id）・`POST /mails`（`throttle:10,1`）・`GET /mails/{id}`（送った人・受け取った人・管理者だけ。ほかは 404）。

```

set PARK_URL=https://www.jona.jp/park
set PARK_AI_TOKEN=（.env と同じ合言葉）
```

### 案件の必須・尚可の読み直し（v0.6.0。2026-11-12）

見ていない案件メールでは、規則（`CaseParser`）だけだと必須・尚可が 6 割前後しか合わない。手元の AI（Ollama の qwen2.5:7b）は 94〜100% だが、1件 1分ほどかかり、元の文を 1% ほど書き換える。そこで、規則の結果をすぐ出し、AI の結果は本文と突き合わせて、自動か人の選択で入れる（`app/Services/CaseAi.php`）。

- **規則の読み方（v3）**：`CaseParser::sections`（必須・尚可の行を返す）と `finishSkills`（業務の拾い出し・本文の技術の追加。規則と AI の両方が通る）。`<<必須>>`・`⇒必須`・`スキル(必須)：`・`【必須】`・`◆スキル：`・`MUST`/`WANT`・`推奨`・`BETTER`、箇条書きの印と番号、見出しと同じ行の本文、区切り線・次の見出し・小見出し・深い `-`・`※` を読む。読めなければ今までの読み方（R9）。取り込みの画面は、今までどおりすぐ規則の結果を出す（AI を待たない）。
- **仕事 `case_skills`**（`ref_type=case`）を入れる時：案件を登録したとき（`store`）、本文を変えて保存したとき（前の順番待ち・未選択の仕事は `dropped`、`ai-case-stale`。本文が空・長すぎでも捨てる。作業中の仕事があっても新しい仕事を入れる）、案件の画面の「AI に読み直してもらう」。合言葉が無い・本文が空・6000字を超える（`CaseAi::MAX_TEXT`）ときは入れない（登録は成功する）。順番待ち・作業中があればボタンでは2つ目を入れない。
- **input（JSON）**：`actor_role`・`prompt`（古い worker 用）・`system`（指示。`CaseAi::PROMPT`）・`user`（本文）・`options`（`{"temperature": 0}`）・`text_hash`（本文の sha1）・`rule`（規則の必須・尚可。`CaseParser::ruleLines`＝`parse` が実際に使う行）・`base`（入れたときの案件の4列）・`edited`（登録の前に人が直したか）。表の列は足していない。
- **本文との突き合わせ**（`CaseAi::restore`）：AI の各項目が本文にそのままあれば `ok`、近い行（隣り合う2行をつないだものも含む。2文字ずつの組の Dice 係数が 0.5 以上。`FIX_LIMIT`）があればその行の文に戻して `fixed`、無ければ `missing`（本文に無い言い方）。
- **自動で差し替える条件**（`CaseAi::compare` の `auto`）：必須・尚可の行数が規則と同じ／`missing` が0／AI の必須・尚可が両方0件ではない（`empty`）／人が直していない（登録の前の `edited`、後の `base` との違い）／案内・案内メール・応募が無い／募集中か下書き／本文が仕事を入れたときと同じ。差し替えるのは `required_skills`・`preferred_skills`・`required_exp`・`preferred_exp` の4つだけ（`CaseAi::apply`）。満たさないときは `done` のまま、登録した人に知らせ（画面だけ）、案件の画面の `#ai` で「AI の結果を使う」（`POST /ai-jobs/{id}/apply-case`）か「今のままにする」（`/drop`）を選ぶ。AI の行が規則とまったく同じなら、仕事を閉じる（「AI も同じ読み方でした」）。本文が変わったあとの結果・選択は使えない。
- **見分け**：`audit_log` の `ai-case-auto`（自動）・`ai-case-same`（同じで閉じた）・`ai-case-stale`（本文が変わった）・`ai-case-apply`（人が使った）・`ai-case-keep`（今のままにした）。これで「自動／選ぶ」の割合を見て、閾値を見直す。
- **見える人**：`Perms::caseEdit`（管理者・その案件の SES・担当者）だけ。エンジニア・ほかの会社の SES には欄も AI の文も出ず、`apply-case`・`drop` は 403。見本データの削除（`SamplePurge`）は、見本の案件の `case_skills` の仕事も消す。
- **worker の `system`・`user`・`options`**：`/ai/worker/next` の答えに、あれば付く。worker は `system` と `user` があれば2通で Ollama に渡し、`options` を既定（`temperature 0.2`・`num_ctx 8192`）の上に重ねる。無い仕事（面談スクリプト・経歴書）と古い worker は、今までどおり `prompt` だけ。
- **worker を新しくする手順**（コードが変わったとき）：worker を動かしている PC（今は GENESIS）で park を `git pull` し、動いている「PARK AI つなぎ役」（`pythonw.exe` の `park_ai_worker.py`）をタスクマネージャーで終わらせ、スタートアップの「PARK AI つなぎ役」を動かして起こし直す（`~/.park-ai/config.json` は変えない）。worker は1台だけにする（取り合いの守りが無いため。PC を移すときは、前の PC の worker を止めてから）。確かめは、架空の本文の案件を登録して、案件の画面の欄が変わるのを見る。

## メールを実際に送るには

最初は `MAIL_MAILER=log` で「保存のみ」（管理者の「メール」画面で中身を確認できる）。送るときは `.env` を設定する（`.env` は Git に上げない）。

```
MAIL_MAILER=smtp
MAIL_HOST=smtp.gmail.com
MAIL_PORT=465
MAIL_SCHEME=smtps
MAIL_USERNAME=送信に使うアドレス
MAIL_PASSWORD=アプリ パスワード
MAIL_FROM_ADDRESS=送信に使うアドレス
MAIL_FROM_NAME="PARK 管理者"
```

`MAIL_FROM_NAME` は、企業名を入れていない管理者のメールと、自動のメール（通知・確認コードなど）の差出人の名前です。企業名を入れた管理者が自分で送るメールは、差出人の名前がその企業名になります。アドレス（`MAIL_FROM_ADDRESS`）は全メール共通です。

設定したら `php artisan config:clear` をして、管理者の「設定」→「テストメールを送る」で確かめる。
