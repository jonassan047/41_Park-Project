## 1. 目的

EG が自分のスキルを登録し、それが案件の候補選びとスキルシートに正しく効くようにする。いちばん大事なのは成約率（2026-10-14 TEZZO）で、そのためには「盛らない・抜けない」スキルの記録が要る（N01「事実を盛らない」、R09「事実にもとづいて作る」）。

## 2. 今の DB（v0.2.0 時点。コードで確かめた）

| 表 | 中身 | 問題 |
|---|---|---|
| `skill_terms` | 技術マスタ（正式な名前・分類・別名）。案件メールから自動で増え、管理者が確かめる | 問題なし。これを軸にする |
| `engineer_skills` | EG のスキル表（名前・分類・年数・レベル 1〜5・`term_id`） | 保存のたびに全部消して入れ直す／年数は自己申告だけで経歴と突き合わない／レベルの意味が決まっていない／同じ技術が2行になりうる |
| `engineer_projects` | 業務経歴。技術は `tech`・`os_tools`・`langs`・`dbs` の4つの**文字列** | 技術がマスタにつながらず、「何を何か月使ったか」を数えられない |
| `engineer_certs` | 資格 | 今回は触らない |

## 3. スコープ

### 3-1. やること

- DB：8章のとおり（今の表を育てる。作り直さない）。
- 画面：EG のスキル表に、レベルの意味の文・最後に使った年月・得意の印・ひとことを足す。経歴から数えた月数を並べて出す。経歴の技術の入力欄はそのまま（文字列）で、候補にマスタの言葉を出す。
- 4つのプレーヤーの権限は 9章（今の動きのまま。直したら EG の「確認しました」をやり直し）。
- Matcher は新しい表＋文字列で読む（点数の計算は変えない）。Excel・Q&A は今のまま文字列を読む。
- 今のデータの移し替え（文字列 → 新しい表。消さない）。

### 3-2. やらないこと

- 資格とマスタのつなぎ、ヒューマンスキル、学習ループ（R11）。
- 経歴の入力を「マスタから選ぶだけ」の形にすること（文字列を正に残すため）。
- Matcher の点数の変更。

## 5. 前提・制約

- 公開版には管理者 TEZZO、テスト用の SES・EG、`@park.example` のダミー（EG 80人。経歴は無い）がいる。`park:purge-samples` は新しい表を `engineer_projects` より前に消し、バックアップにも入れる。仮登録の取り消しも新しい表を消す。
- テストは SQLite で動くが、本番は MySQL（照合順序 `utf8mb4_unicode_ci`）。移し替えは手元の MariaDB（捨ててよいテスト用の DB）でも流して確かめる。
- 個人情報は公開リポジトリに書かない。

## 6. 完了の条件

- EG が、スキル表に技術・レベル（S04 の文）・申告年数・最後に使った年月・得意の印・ひとことを保存できる。マスタに無い技術も入れられ、管理者の確かめ待ちに出る。41 文字以上は断られる。
- EG が経歴を保存すると、新しい表がその文字列から作り直され、スキル表に経歴から数えた月数が出る（S13 の端を含む）。S03 の条件のときだけ注意が出る。
- SES・担当者（自社の EG）・管理者が直すと、EG の「確認しました」がやり直しになる。他社の EG は 403。仮登録中の EG は上位が直せない（AI の下書きの取り込みも含む）。
- マスタの「まとめる」が新しい表を含めて通り、途中で失敗しても元に戻る。
- Matcher の点数、Excel のスキルシート、Q&A の結果が今と変わらない（今のテストが通る）。
- 移し替えを2回流しても同じ結果で、マスタは増えない。今の経歴の文字列は残っている。MariaDB でも通る。
- 見本のデータを消す処理と、仮登録の取り消しが、新しい表があっても通る。
- 上の全部が、テスト設計書の項目になり、エビデンスが残っている。

## 8. DB の設計

### 8-1. 図

```
skill_terms（技術マスタ）
   ▲ term_id                ▲ term_id
   │                        │
engineer_skills          engineer_project_skills ── 文字列から作る索引（S02）
（EG のスキル表）          （経歴ごとに使った技術）
   │ engineer_id            │ project_id
   ▼                        ▼
engineers ◀── engineer_id ── engineer_projects（業務経歴。技術の文字列が正）
```

### 8-2. `skill_terms`（今のまま）

変えない。分類は lang・fw・db・os・cloud・infra・tool・method・domain・role・other（コードの実際）。新しい表とスキル表に入れるのは、技術の分類だけ（S11）。

### 8-3. `engineer_skills`（列を足す）

| 列 | 型 | 今 / 足す | 意味 |
|---|---|---|---|
| `id` | bigint | 今 | |
| `engineer_id` | FK engineers（消すと一緒に消える） | 今 | |
| `term_id` | bigint（`skill_terms`） | 今 | 新しい行は必ず入れる。今ある空の行は残る（S06） |
| `name`・`category` | string | 今 | マスタの写し（表示用） |
| `years` | decimal(4,1) | 今 | 本人の申告の年数（S03） |
| `level` | int 1〜5 | 今 | S04 の意味 |
| `last_used_ym` | char(7) YYYY-MM、空可 | 足す | 最後に使った年月（空なら経歴から出す） |
| `is_primary` | boolean、既定 false | 足す | 得意の印（スキルシートの頭に出す。5つまで） |
| `note` | string(200)、空可 | 足す | ひとこと。名前を伏せたシートには出さない（S15） |
| `created_at`・`updated_at` | datetime、空可 | 足す | 今ある行は空のまま |

索引：`(engineer_id, term_id)`。一意にはしない（S05）。

### 8-4. `engineer_project_skills`（新しい表）

| 列 | 型 | 意味 |
|---|---|---|
| `id` | bigint | |
| `project_id` | FK engineer_projects（消すと一緒に消える） | どの経歴か |
| `term_id` | FK skill_terms | どの技術か（技術の分類だけ。S11） |

一意：`(project_id, term_id)`。`engineer_id` は持たない（経歴から引く。消すときの FK のぶつかりを避ける。H4）。

作り方（S02）：経歴の4つの文字列を `project_techs()` で分け、マスタで引く。見つかった技術の分類の言葉だけを入れる。その経歴の行をいったん消して入れ直す（索引なので、作り直しでよい）。

### 8-5. 経歴から数えた月数（保存しない）

技術ごとに、その技術が付いた経歴の期間を月の集まりにし、重なりを1回として数える。例：2019-04〜2020-03 と 2020-01〜2020-06 で Laravel → 15 か月（重なった3か月は1回）。端は S13。保存せず、表示と候補選びのときに計算する（経歴を直せば自動で合う）。

### 8-6. 移し替え（S09）

1. 表を作るマイグレーション：新しい表と、`engineer_skills` の新しい列。
2. データを入れるマイグレーション：すべての経歴に、8-4 の作り方で索引を作る（`insertOrIgnore`）。マスタには足さない。
3. どの行も消さない・書き換えない。down は新しい表と新しい列を落とすだけ（元の文字列は残っているので戻せる）。
4. 公開版への反映は常時了承の範囲（コードと migrate）。新しい表に足すだけ。

## 9. 権限（4つのプレーヤー）

| 操作 | 管理者 | SES | 担当者 | EG |
|---|---|---|---|---|
| 自分のスキル表・経歴を直す | － | － | － | ○ |
| 自社の EG（参加中・停止中）のスキル表・経歴を直す | ○（全員・直属） | ○ | ○ | － |
| 仮登録中の EG を直す（AI の下書きの取り込みを含む） | × | × | × | － |
| 他社の EG を直す | ○ | ×（403） | ×（403） | × |
| マスタを確かめる・まとめる | ○ | × | × | × |

- EG 以外が直したら、EG の「確認しました」（`engineers.self_confirmed_at`）を消す（今の動きのまま）。
- 兼任の人（管理者・担当者を兼ねる EG）は、入るときに選んだ立場で判定する（S07）。エンジニアの立場で自分を直すのは「本人」。
- 退会済の EG の扱いは今のまま（v0.3.0 では変えない）。
